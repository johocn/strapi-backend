第三章关键机制与方法

本章说明系统内置的机制与规则。运营者了解这些机制后，可以准确预判"名额满了会怎样""有人取消会怎样""费用什么时候扣"等行为，避免误操作。

3.1 名额并发控制

报名高峰时可能多人同时提交。系统采用事务内原子更新已用名额并校验不超过容量上限的方式保证并发安全：

  • 报名时在数据库事务内对 usedCapacity 做原子递增，并校验 usedCapacity ≤ capacity
  • 名额未满 → 报名成功（active）；名额已满 → 自动进入候补（waiting）
  • 不引入 Redis 悲观锁等额外组件，机制简单可靠
对运营的意义

并发安全由系统保证，运营者无需预锁名额。满员后新报名会自动转为候补，不需要运营手动"加名额"来承接溢出流量（除非有意扩容）。

3.2 候补与递补

这是报名体系的核心机制，务必理解：

场景系统行为
报名时满员自动转为候补 waiting，不占名额，不做费用扣减
已报名（active）取消状态置 cancelled，释放名额，并自动递补最旧的候补转正（按报名时间 + 记录 id 升序），转正用户按规则扣费并收到 act_promoted 转正通知
候补（waiting）取消仅置 cancelled，不减名额、不触发递补
管理端移出候补adminCancelSignup 仅允许操作候补状态；对 active 状态报名执行移出会返回 400

转正通知使用去重键（dedupeKey）保证幂等，重复递补场景不会重复通知用户。

3.3 计费模式

活动报名费用支持三种模式与两种收取时点：

配置取值说明
计费模式
pricingMode		flat一口价：固定 pointsCost 积分（或 cashPrice 现金）
tier档位：feeTiers 定义多个价格档（如早鸟/标准/现场）
factor因子：feeFactors 按因子（人数/时长等）计算费用
收取时点
feeCollectAt		signup / checkinsignup：报名时扣分/收款；checkin：到场签到时收取

报名记录会保存实际扣点 pointsCharged，C 端报名前可通过费用预览接口确认本次应付。

3.4 签到核销

签到方式由 checkinMode 控制：

模式说明核销方式
worker_scan仅工作人员扫码运营端扫码核销（adminScanCheckin）
self仅用户自助C 端自助核销
both两种均可以上两者兼支持

签到成功写入到场时间 attendedAt，到场记录标记核销方式（worker_scan / self）。如开启地理围栏（geoEnforced + geoRadiusM），自助核销还会校验用户位置是否在活动场地半径内。

3.5 对账结算

活动结束后，运营者可基于报名/到场数据做经营对账：

  • 台账（ledger）：对活动的报名、到场、费用进行快照汇总；可重新生成（regenerateLedger）以反映最新数据
  • 结算（settle）：确认讲师/场地结算金额（settleLecturer / settleVenue）并完成结算标记
  • 台账列表 GET /adm/ledgers、生成 POST /adm/activities/:documentId/ledger、结算 PUT /adm/ledgers/:documentId/settle

3.6 分享裂变与奖励

活动支持分享裂变拉新：用户分享活动带来的新报名可获得积分奖励（shareRewardPoints），并可通过裂变排行榜（GET /adm/activity-share/leaderboard）查看各用户的邀请成效，用于运营激励。

3.7 报名表单与内容解锁

活动可自定义报名收集字段（formConfig），每个字段包含 key / label / type / required / 最小值 / 最大值 / 选项 等配置，报名时用户填写的信息保存在报名记录的 formData 中，运营端报名名单可展开查看。

同时可配置报名后解锁权益（preUnlockArticles / preUnlockLessons），报名记录写入 unlockInfo 记录已解锁内容，形成"报名即得学习权益"的转化钩子。

重要边界

退款/逆向积分：报名取消不自动退积分，积分处理按配置规则执行；涉及退款需求时请单独确认积分服务对目标方法的支持情况，不要假设存在直接对应方法。
